How lapce-app fits together

lapce-app is the Floem frontend for the read-only code browser. One application manages windows. Each window has one root session. That session connects the editor layout, shared documents, panels, and backend RPC.

Read the current model. This report describes the working tree, including the uncommitted single-root change. WindowTabData is now the session for one window. Its name does not mean that workspace tabs still exist.

1. Start with the window and its session

AppData

Application-wide state.

windows is a signal containing a map from WindowId to WindowData. Other fields track the active window, settings, configuration watcher, application commands, and log filter.

Source: app.rs:124

WindowData

One operating-system window.

session: RwSignal<Rc<WindowTabData>> holds one session reference. position, window_scale, root_view_id, and ime_enabled describe the window.

ReloadRoot saves the old layout, shuts down its proxy, creates a session for the same root, and replaces the signal value.

Source: window.rs:50

WindowTabData

The controller for one root/session.

It stores main_split, the panel controllers, proxy, and common. It dispatches internal commands and handles backend notifications.

workspace: Arc<LapceWorkspace> is the root/connection context. That type now has kind and path. It is not a list of workspaces.

Source: window_tab.rs:155

2. Shared state crosses the tree

Controllers need the same command routes, settings, and focus state. They receive shared handles instead of copies of every value.

CommonData

Shared state within one root/session.

Rc<CommonData> connects editors, documents, panels, and the palette. It contains command listeners, configuration, focus, search state, completion state, root actions, and a clone of ProxyRpcHandler.

common.window_common points to the same window-level state held by WindowData.common.

Source: window_tab.rs:115

WindowCommonData

Shared state for the operating-system window.

It holds window_command, window size, scale, maximize state, input-method state, and cursor-blink information. It has no workspace-tab count or tab-header state.

3. Separate layout, views, and file state

MainSplitData

The editor area and its registries.

root_split identifies the top layout node. splits and editor_tabs map IDs to reactive layout records. editors holds the editor-view registry.

documents stores WorkspaceDocuments<Rc<Doc>>. The public docs and scratch_docs fields are projections into that model. They are not extra document copies.

Source: main_split.rs:377

EditorTabData

A group of editor tabs inside a split.

SplitData.children contains a size signal and a SplitContent for each child. A child is another split or an editor tab group, selected by ID.

EditorTabData.children contains EditorTabChild values. A child can identify a file editor, diff editor, settings view, theme-color view, or keymap view. active selects a child in that group.

An editor tab group is distinct from the removed workspace tabs.

Source: editor_tab.rs:401

EditorData

One editor view and its UI state.

editor: Rc<floem::views::editor::Editor> holds the Floem editor handle. The Floem editor stores the cursor, viewport, scroll signals, and a document reference. EditorData adds tab membership, confirmation state, inline find, sticky headers, and shared session access.

Editors indexes these views by EditorId. This registry also contains local text inputs, such as palette and search inputs. An editor entry does not always represent a source file.

A plain EditorData.clone() shares its handles. EditorData::copy creates a new view over the same Doc.

Source: editor.rs:203

Doc

The Floem adapter for shared document state.

Doc connects the engine model to reactive UI fields, rendering caches, diagnostics, and the backend open/close lifecycle. MainSplitData::get_doc reuses its cached Rc<Doc> for an existing path.

EditorData::doc() obtains that adapter through the Floem editor. DocSignal is a typed wrapper for the Floem document signal.

Opening one file in two views can share the text and syntax model without sharing the two view cursors. The file cache belongs to one session. Another window can have its own Doc for the same path. Local input documents can exist outside the file-path cache.

Source: doc.rs:88

Source: main_split.rs:72 · editor_tab.rs:163 · main_split.rs:219 · main_split.rs:616 · editor.rs:3016

The model under Doc

  1. Doc.model: DocumentModel connects engine state to Floem signals.
  2. DocumentModel.document: RwSignal<SessionDocument> stores the session-owned document.
  3. SessionDocument.document: lapce_engine::document::Document stores file identity, content type, loading state, buffer, syntax, and inlay hints.
  4. SessionDocument.synchronization stores optional DocumentSync state for the backend attachment.

DocumentField is an alias of ModelField<SessionDocument, T>. Its getters and setters access a field of the same session model and notify the relevant observers. The document’s public buffer and syntax fields therefore access that same model.

Two uses of the name Document: Floem has a Document trait for editor integration. Doc implements that trait. The concrete lapce_engine::document::Document holds shared document data.

How diff views fit

MainSplitData.diff_editors indexes DiffEditorData. Each diff has left: EditorData and right: EditorData. A tab group refers to the diff by DiffEditorId. Each side has its own document reference. One side can use history text and the other can use the current file.

5. Commands and RPC connect the parts

Commands on the UI side

  • AppCommand: application and OS-window actions.
  • WindowCommand: open another root window, reload the same root, create a window, or close one.
  • LapceCommand: a command plus its kind and optional data.
  • LapceWorkbenchCommand: high-level actions, such as Open File.
  • InternalCommand: typed UI actions, such as GoToLocation.

WindowTabData::new attaches listeners to the session commands. Its handlers dispatch work to MainSplitData and the panel controllers.

ProxyData: the backend adapter

ProxyRpcHandler sends requests and notifications. BackendControl requests backend replacement. notification exposes backend events as a Floem read signal. CoreRpcHandler is also retained as a handle.

new_proxy creates a lapce_client::managed::ManagedBackend. The managed client owns connection workers. Its connection selects the embedded backend, an external process, an external socket, or SSH.

The adapter routes terminal bytes to the terminal update channel. It converts other backend events into the UI notification signal.

Source: command.rs:718 · window_tab.rs:518 · window_tab.rs:1315 · proxy.rs:22 · managed.rs:22 · lib.rs:75

These are three different structures. The struct hierarchy describes state and handles. The split tree describes screen layout. The thread layout describes execution. They do not have one-to-one relationships.

6. Follow one file from input to view

Source trace: opening src/lib.rs. The filename is illustrative. The method order and asynchronous boundaries come from the implementation. No execution timing is implied.

  1. Choose a file

    A view or startup code sends InternalCommand::GoToLocation with an EditorLocation.

    Source: window_tab.rs:1374

  2. Find or create its Doc

    MainSplitData::go_to_location calls get_doc. WorkspaceDocuments::file returns the existing adapter or creates one.

    Source: main_split.rs:616

  3. Request the file text

    For a new document, get_doc captures a SessionOpening and sends its request through common.proxy.request_async.

    Source: main_split.rs:640

  4. Create or select the view

    The layout code selects an EditorTabChild. Editors creates or finds an EditorData, whose Floem editor points to the Doc. This can happen while loading is pending.

    Source: main_split.rs:661

  5. Return to the UI thread

    The RPC callback uses create_ext_action. Its UI closure calls Doc::finish_opening with the captured opening and the response.

    Source: main_split.rs:647

  6. Update shared state and views

    DocumentModel applies the response to SessionDocument. It notifies loading and relevant model observers. Doc then refreshes its document-related UI work on success.

    Source: model.rs:41

Reuse and failure: an existing cached document avoids the new-file open request. The opening transition records failure in the shared loading state. A stale opening does not get to replace a newer attachment. Backend disconnect and reconnect events run through WindowTabData::handle_core_notification, which updates or reopens the document attachments.

8. A useful source-reading order

  1. app.rs: launch → create_windows → app_view. Find where the top-level state and views are created.
  2. window.rs: read WindowData, WindowCommonData, and run_window_command.
  3. window_tab.rs: read the session fields, its constructor, and the command/notification handlers.
  4. main_split.rs: read the registries, get_doc, and go_to_location.
  5. editor_tab.rs, editor.rs, and doc.rs: separate layout, per-view state, and document state.
  6. doc/model.rs and reactive_model.rs: follow field access into the shared engine model.
  7. proxy.rs and db.rs: follow the backend and persistence boundaries.
